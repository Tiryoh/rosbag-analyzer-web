# ADR: loader のコンソール出力を 1 ロードあたり一定の行数に抑える

- Status: Proposed
- Date: 2026-08-31

## Context

ブラウザ内で完結するアプリでバックエンドもテレメトリも無いため、`console` が実質唯一の診断チャネルである。その結果、loader には開発時のログがそのまま残っていた。

問題は 2 つある。

1 つ目は **出力行数がファイルサイズに比例する箇所が 3 つあった** こと。

- rosout メッセージ 100 件ごとに 1 行 → 50 万件の bagで 5,000 行
- bz2 / lz4 チャンクを展開するたびに 1 行 → 圧縮された bagのチャンク数だけ
- コネクションごとに 1 行 → トピック数の多い bagで数百行

devtools を開いた状態では `console` への出力が同期的に処理されるため、その分だけロードが遅くなる。レコードごとにログを出す方式では、ファイルが大きいほど待ち時間が積み上がる。ADR 0010 で進捗の yield を件数ベースから経過時間ベースに変えたのも、同じ理由による。

2 つ目は、1 回のロードで約 25 行の内訳ログ（`Opening bag...`、`State updated successfully` など）が出ており、**実際に問題が起きたときに重要な行が埋もれていた** こと。

## Decision

loader のコンソール出力を、ファイルサイズによらず 1 ロードあたり一定の行数に抑える。レコード・チャンク・コネクション単位のログは出さない。

## Decision Details

正常系で出すもの:

- ロード開始 1 行（形式・ファイル名・サイズ）
- 発見したトピックの要約 1 行
- reindex 経路に入ったときのみ、開始と完了で各 1 行
- 収集結果の件数（rosout / diagnostics で各 1 行）

異常系で出すもの:

- 失敗時は `console.error` 1 行。`Error` オブジェクトをそのまま渡す（devtools が stack を展開するので、種別・メッセージ・stack を別々に出す必要はない）
- bag のマジックバイトが期待と違うときだけ、先頭 20 バイトを `console.warn`。正常なファイルでは出ない

出さないもの:

- 中間状態のナレーション（`Opening bag...`、`Calling loadMessages...`、`State updated successfully` など）
- ループ本体からの出力（レコード・チャンク・コネクション単位）

## Alternatives Considered

### Alternative 1: すべて削除する

不採用。
バックエンドが無いため、「ファイルが読めない」と報告されたときに console 以外の手がかりが無い。件数の要約は、問い合わせを受けたときにユーザーから伝えてもらえる最小限の診断情報なので残す。

### Alternative 2: デバッグフラグで詳細ログを切り替える

不採用（将来再検討可）。
`src/core/` は DOM 非依存を保つ必要があり（ADR 0008）、`localStorage` や URL クエリを直接参照できない。フラグを web 側から注入する仕組みを足すことになり、「行数を定数にする」という今回の目的に対して大きすぎる。詳細ログが実際に必要になった時点で検討する。

## Consequences

### Positive

- 1 ロードあたりの出力が約 25 行から 4〜6 行になり、ファイルサイズに依存しなくなった
- 失敗時に読むべき行が埋もれない

### Negative

- 「どのステップで止まったか」を console から追えなくなる。失敗時は例外と stack で判断する
- 診断情報を足したくなったときに、「1 行だけなら」とループ内にログを書き戻してしまいやすい。これは下の guardrail 1 で禁じる

## Verification / Guardrails

1. loader の `console` 呼び出しをループ本体（レコード・チャンク・コネクション単位）に置かない
2. 1 ロードの出力行数はファイルサイズに依存しない。同じ内容でレコード数だけ N 倍のファイルを読んでも行数は増えない
3. 正常系で出すのは要約のみ。バイト列などの詳細は異常を検出したときだけ出す
4. `src/core/` はログのためにブラウザ API を参照しない（ADR 0008）
