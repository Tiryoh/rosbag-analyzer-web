# ADR: ローカル LLM によるログ質問機能を現時点では導入しない

- Status: Accepted
- Date: 2026-07-26

## Context

本プロジェクトで、ブラウザ内の WebAssembly / WebGPU 対応 LLM を使い、読み込んだログについて自然言語で質問できる機能を検討した。
サーバーへログを送信せず、初回取得後はオフラインで動作する構成として WebLLM を評価した。

評価用に、次の要素を持つブラウザベンチマークを実装した。

- WebLLM のモデルをブラウザ上で順に読み込み、同一の質問を実行する
- ROS ログを模した 10 件の合成テストケースを使う
- 回答、根拠としたログ行 ID、回答不能フラグを JSON で要求する
- 必須語、禁止語、根拠行、回答不能判定を決定論的に採点する
- Cache API、IndexedDB、OPFS のキャッシュ方式を切り替える
- 結果を JSON / CSV で保存する

ベンチマーク実装は、この ADR を導入したブランチの先行コミット
`Add local WebLLM benchmark harness` に保存する。
本番アプリで利用しない依存関係とコードを main の最終ツリーへ残さないため、その後のコミットで削除する。

実機ブラウザで得られた結果は次のとおりだった。

| モデル | 合格 | 平均スコア | 主な問題 |
| --- | ---: | ---: | --- |
| `gemma-2-2b-jpn-it-q4f16_1-MLC` | 4 / 10 | 0.652 | ERROR 件数の誤答、根拠不足時の回答不能判定失敗 |
| `Qwen2.5-1.5B-Instruct-q4f16_1-MLC` | 1 / 10 | 0.375 | ログにないモータードライバー故障原因の生成、件数の誤答 |
| `Llama-3.2-1B-Instruct-q4f32_1-MLC` | 1 / 10 | 0.342 | 出力形式の不遵守、根拠行の誤選択、日本語回答の品質不足 |
| `gemma-2-2b-it-q4f16_1-MLC` | 実行不能 | - | モデル shard の IndexedDB 取得に失敗 |

モデルの初回取得時には Cache API の内部エラーとストレージ容量超過も発生した。
キャッシュ方式やモデルごとの削除で一部を回避できたが、複数モデルを安定して取得・保持できる状態ではなかった。

ログ解析では、存在しない原因の生成、件数の誤答、根拠不足時の断定が誤った調査判断につながる。
今回の結果は、利用者が検算せずに使える品質には達していない。

## Decision

ローカル LLM による自由形式のログ質問機能は、現時点では本番アプリへ導入しない。

件数、最初または最後のエラー、重要度、ノード、時刻範囲など、正確性が必要な問い合わせは、構造化されたログデータに対する決定論的な処理で実装する。

将来 LLM を導入する場合も、LLM にログ全体の検索や事実判定を任せない。
アプリ側で抽出した根拠行を入力とし、その内容の要約や言い換えに用途を限定する。

## Decision Details

### 本番コードに含めないもの

- `@mlc-ai/web-llm` 依存
- モデル選択、取得、キャッシュ管理の UI
- 自由形式のログ質問 UI
- 今回作成したブラウザベンチマーク

ベンチマークは評価過程の再現用として GitHub Pull Request のコミット履歴に残す。

### 再評価条件

次の条件を満たす候補が現れた場合は、導入可否を改めて判断する。

1. WebLLM から利用できる量子化済みモデルと対応する WebGPU 用ライブラリが安定して配布されている
2. 対象ブラウザで、モデル取得、容量不足からの復旧、キャッシュ後のオフライン起動を再現できる
3. 実ログの特徴を反映した、今回より広い評価セットで品質を測定できる
4. 根拠のない回答、件数の誤答、回答不能判定の失敗をリリース阻止条件として扱える
5. モデルサイズ、ロード時間、推論時間がログ解析の補助機能として許容できる

Gemma 4 E2B など新しい小型モデルも、WebLLM 用 artifact と model library が利用可能になった後に同じ基準で評価する。

## Alternatives Considered

### 最も成績が良かった Gemma 2 2B JPN を採用する

不採用。
他候補より良好だったが合格は 4 / 10 であり、ERROR 件数と回答不能判定を誤った。
ログ解析機能の既定モデルとして提供できる品質ではない。

### Qwen 2.5 1.5B または Llama 3.2 1B を採用する

不採用。
モデルサイズは比較的小さいが、根拠選択、形式遵守、存在しない原因の生成に問題があった。

### 外部 LLM API を利用する

不採用。
ログを外部へ送信する構成になり、オフラインファーストかつバックエンド不要という本プロジェクトの制約と一致しない。

### 決定論的な問い合わせだけを提供する

必要になった時点で個別に検討する。
自然言語生成を使わず、既存のフィルタ・集計処理を拡張するため、正確性とオフライン動作を維持できる。

## Consequences

### Positive

- 根拠のない回答を公式機能として提示するリスクを避けられる
- 大容量モデルの取得、保存、キャッシュ復旧をユーザーに要求しない
- 本番バンドルへ WebLLM とモデル管理コードを追加せずに済む
- 将来の再評価に使える実装と判断材料は Pull Request の履歴から参照できる

### Negative

- ログへ自然言語で質問する操作は提供されない
- 新しいモデルを評価する際は、Pull Request の先行コミットからベンチマークを復元する必要がある
- 決定論的な質問機能を追加する場合は、問い合わせごとに抽出・集計処理を実装する必要がある

## Verification / Guardrails

1. main の依存関係に `@mlc-ai/web-llm` を含めない
2. main の本番コードと開発用コードにモデル取得処理を含めない
3. 正確性が必要なログ集計は LLM の出力だけで確定しない
4. 将来の評価では、根拠行 ID と回答不能判定を含む機械採点を継続する
5. 導入判断には品質だけでなく、初回取得、ストレージ容量、キャッシュ後のオフライン動作を含める
